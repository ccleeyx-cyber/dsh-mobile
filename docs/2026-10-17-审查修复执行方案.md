# DSH Mobile 审查修复执行方案

> 2026-10-17 全面审查（UI / 功能 / 代码 bug / 操作逻辑 / 安全）的修复计划。
> 审查方法：6 路并行代码审查 + 关键发现逐条回源码核实行号 + 基线验证
> （flutter analyze 0 问题 / flutter test 760 全过 / 网关 hermetic 408 过 1 跳）。

## 全局约束（先读）

1. **绝不重启 dsh web**：网关插件（dsh-server-plugin）的改动写完不生效，直到用户
   自己重启。每个网关阶段完成后，把重启步骤明确交给用户，本阶段内先做不需要重启的
   客户端部分。
2. **测试不污染真实数据**：只跑 hermetic（`npm test` / `flutter test`）；
   live/e2e/destructive 只在用户显式点名时跑。新增测试一律走既有注入缝
   （`debugSet*` / fake 识别 / mkdtemp 隔离）。
3. **发布流程**（README §3）：改 `pubspec.yaml` 版本 + 写 `CHANGELOG.md` 同名小节 +
   push 到 main → CI 构建并更新 GitHub Release。不打包进本机。
4. **每个「空操作修复」类缺陷必须带一个钉住行为的测试**——本次 4 处
   「注释声称已修、代码未生效」全是缺端到端验证造成的。

## 阶段 1：P0 客户端缺陷（dsh_service / chat_view / voice）

全部在 `dsh_mobile/lib/` 下，无需动网关。

### 1.1 重连耗尽后手动重试失效【严重】
- 位置：`services/dsh_service.dart:769-775`（retryConnection 只重置 attempts）、
  `:5033`（_scheduleReconnect 入口早退）、`:5079`（armReconnectRetry 全工程零调用）。
- 修法：`retryConnection()`、`handleAppResumed()`、`selectSession()`、
  下拉刷新入口统一改为调用 `armReconnectRetry()`（真调用，删掉假注释）。
- 测试：单测驱动 8 次 `_executeReconnect` 失败 → 断言 `reconnectExhausted == true`
  → 调 retryConnection → 断言重新排定重连（可用注入的假 channel）。

### 1.2 _executeReconnect 缺 await ready + 无 connectTimeout【严重】
- 位置：`dsh_service.dart:5086-5165`（对照 connect() 的 :954）；两处
  `IOWebSocketChannel.connect`（:901 / :5102）。
- 修法：
  - `_executeReconnect` 里补 `await _channel!.ready` + catch（与 connect() 对称）；
  - 两处 connect 加 `connectTimeout`（建议 10s）；
  - 删掉 :5156 被 status 守卫拦成 no-op 的死 ping，或改为 ready 之后的真探测。
- 测试：假 channel 永不发帧 → 断言一段时间后状态从 connecting 走向重连调度，
  而不是永久卡住。

### 1.3 取消栅栏误伤远端新回合【高】
- 位置：`dsh_service.dart:4619/4655/4679`（`_activeTurnSeq <= _cancelledTurnSeq`
  丢弃帧）、`:4481`（session_status 同条件）、`:1859`（轮询强制 isRunning=false）、
  `:1982`。
- 修法：收到当前会话 `session_status isRunning:true` 的上升沿（`!_turnRunningSeen`
  处，:4490）或对账发现新的 user 消息时，回落栅栏
  （`_cancelledTurnSeq = _activeTurnSeq - 1`）。长期正解是 turnId 匿名化，
  但回落栅栏先止血。
- 测试：单测模拟「取消 → 远端新回合 delta 帧」序列，断言新回合帧不再被丢。

### 1.4 轮询对账重建消息丢字段【高】
- 位置：`dsh_service.dart:1834-1855 → 1970`（reconcile 构造 ChatMessage 不带
  attachments / turnTokens / noticeKind / noticeVariant / noticeChildId /
  noticeBody）；三处解析漂移（:1418 / :544 / :1837）。
- 修法：抽统一的 `ChatMessage.fromJson` 工厂（放 models/chat_message.dart），
  三处全部改用它；reconcile 换消息时保留旧消息的本地附件元数据。
- 测试：现有 `session_history_reconcile_test.dart` 扩一个用例：
  带附件+turnTokens 的消息过一轮 reconcile 后字段仍在。

### 1.5 isSessionRunning 恒真（空操作修复）【高】
- 位置：`views/chat_view.dart:643-653`（dshRunningId 与 currentSession 自比恒真）。
- 修法：DshService 暴露真正的 `sendingSessionId`（`_isSending` 置 true 的各写入点
  一并记录会话 id，:1450/:1641/:4482/:4634/:4671 等），chat_view 改用它。
- 测试：debugSetRunning 扩展为带 sessionId；widget 测试断言别的会话运行时
  本会话不显示停止键。

### 1.6 语音 onAutoStopped 自赋值（空操作修复）【严重，一行修】
- 位置：`services/voice_input_service.dart:271`。
- 修法：`onAutoStopped = onAutoStopped;` → `this.onAutoStopped = onAutoStopped;`
  （fake 分支与真实分支都要挂）。
- 测试：`voice_start_test.dart` 补一个：start 后触发引擎 done 状态 →
  onAutoStopped 回调到达（fake 钩子路径 + onStatus 路径各一条）。

### 1.7 清空凭据复活【高】
- 位置：`services/storage_service.dart:394-410`（_writeSecrets 只写非空、从不

- 测试：secure_store / storage_service 既有测试文件里各补一个删除-不复活用例。

### 1.8 附带小修（同批顺手）

## 阶段 2：默认模型链路修复（用户报告）

症状：设置页设置默认模型后，新建会话没有用上。三层原因：

| 层 | 断点 | 位置 |
|---|---|---|
| 客户端 | createNewSession 不重置 _currentSessionModel，新会话携带上一会话遗留值 | dsh_service.dart:1491,1529,1558 |
| 网关 | sessions/create 不收 model；prompt 收了 jsonBody.model 但转发 RPC 时丢弃 | index.js:3709-3716, 3807-3822 |
| 引擎 | settings.yaml 的 agent-default-model 写完不重启 dsh web 不采用（已有注释记录） | dsh_service.dart:2126 注释 |

### 修法（按优先级）

1. **客户端主修**（立即生效、不依赖重启引擎）：
   - `createNewSession()` 开头 `_currentSessionModel = null;`（新会话不该继承
     上一会话的模型）；temp/real SessionMeta 的 model 取
     `_settings?.currentModel ?? ''`。
   - 新会话创建成功后（:1572 follow 之后），若 `_settings?.currentModel` 非空，
     主动调一次 `selectSessionModel(realSessionId, default)` —— 这条 RPC 通道
     已被 v1.24 验证立即生效（[fix 2026-10-16]），把「默认模型」按会话级注入，
     绕开引擎重启问题。
2. **网关兜底**：
   - `sessions/create` 接受可选 `model`，非空时在 create 成功后同样调
     `session/selectModel` RPC（复用 :3983 的 resolveModelSelection）。
   - `sessions/prompt` 转发客户端 `model` 字段：非空且与该会话当前选择不同 →
     先 selectModel 再 prompt（防御老客户端）。
   - ⚠️ 此层写完不生效直到用户重启 dsh web —— 交付时说明。
3. **UI 诚实性**：设置页默认模型条目补一句「立即对新建会话生效（App 会按会话
   注入）；引擎全局默认在重启 dsh web 后完全对齐」。

### 测试
- 客户端：注入缝测 createNewSession → 断言新会话 model == 设置默认值、
  selectSessionModel 被调用；上一会话用别的模型时不被继承。
- 网关：hermetic 单测 create 带 model → 断言转发了 selectModel（mock RPC）。

## 阶段 3：网关安全 + jobs/follow（dsh-server-plugin）

⚠️ 本阶段全部需要用户重启 dsh web 后生效；先改代码 + 跑 hermetic 测试，
交付时附重启步骤。

### 3.1 未鉴权配对码铸造【严重】
- 位置：`lib/index.js:2859-2944`（/pair/qr、/pair/info 在鉴权门前自助发码）。
- 修法（二选一，建议都做）：
  a) 默认要求鉴权：这两条路由改为接受 admin token（电脑端扫码页本来就持有）；
  b) 无 token 时仅当请求来源是私网地址（RFC1918 + loopback）才放行，
     公网来源 403 并提示走设置页生成。
- 保留：pair 码本身的随机/TTL/锁定机制不动（那部分是好的）。
- 测试：hermetic 单测：公网 IP 无 token GET /pair/qr → 403；私网 → 200；
  带 admin token → 200。

### 3.2 鉴权爆破退避两处绕过【高】
- `lib/core.mjs:1147-1154`：authFailKey 默认不信 XFF——新增配置项
  `trustProxy`（默认 false），仅显式开启时才用 XFF 首值做退避键。
- `lib/index.js:4242-4267`：WS upgrade 401 路径补 `noteAuthFailure(req)`。
- 测试：伪造不同 XFF 连续 401 → 退避仍触发；WS upgrade 连续错 token → 退避触发。

### 3.3 readonly 白名单反转为 deny-by-default【高】
- 位置：`lib/index.js:3093-3133`。当前白名单漏了
  workspaces/create、approval-presets/save|delete、push/auto-topic、
  quick-commands/run、goals/create|edit、sessions/fork。
- 修法：反转——`POST/PUT` 一律视为写并拒绝 readonly，除非路径在显式的
  `READONLY_ALLOWED_POST` 例外表（目前只读的 POST 很少，逐个审）。
- 测试：遍历全部已注册 POST 路由 × readonly 设备 → 断言只有例外表内放行
  （防将来新增路由再漏）。

### 3.4 jobs/follow 的 collect- 前缀失配【高，功能性】
- 位置：`lib/index.js:767`（collect- 前缀）vs `:2109`（只路由 oneshot-）。
- 修法：`handleUpstreamMuxMessage` 的前缀判断改为
  `startsWith('oneshot-') || startsWith('collect-')`（pendingOneshot 是共用的）。
- 测试：现有单测改为走真实 mux 分发路径注入帧（当前测试注入在 readStreamFrames
  内部，测不到这条路径——这正是漏网原因）。

### 3.5 同批网关健壮性（小项，顺手）
- permStore.forSession 键归一化（core.mjs:1092-1095）。
- 附件读取：Buffer 收集替代 `data += chunk`，加尺寸上限 + upload 同款频率桶
  （index.js:3226-3257）。
- WS upgrade 鉴权失败也写 audit。

## 阶段 7：架构重构（独立分支，不阻塞上述阶段）

拆 dsh_service.dart（5290 行 God-class）：
- `DshApiClient`：纯 HTTP，约 40 个端点，无状态、可 mock；
- `WsTransport`：连接 / 心跳 / 重连 / 退避，单一 ConnectionStatus 流；
- `SessionController`：会话状态机 + 消息对账 + 取消栅栏（1.3 的 turnId 化在此做）；
- `InsightsStore`：队列 / 交付物 / 作业 / 统计，独立通知域。
- 拆分顺序：先 ApiClient（最机械）→ WsTransport → 其余；每步保持
  flutter test 全绿，接口不变、只挪位置，行为变化单独开 PR。

收益实证：三处消息解析漂移（阶段 1.4 的根因）在统一 fromJson 后消失；
「任一变化全 App 重建」随通知域拆分缓解。
